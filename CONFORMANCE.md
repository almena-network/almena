# Conformance — `almena`

Which sections of `SPECS.md` this repository owns, and how much of each is built. The rule is
**`SPECS.md §13.13`**:

- **The matrix belongs to the project.** The specification says what must exist; this file says
  where it lives and how far along it is. `SPECS.md` keeps nobody's accounts.
- **A section closes where it is implemented, not where it is read.** A row moves to *done* when
  it points at code whose behaviour matches its section — not when something compiles or its
  tests pass.
- **When `SPECS.md` changes, the affected rows go to *under review*** until someone checks them
  against the new text.
- **If code and the specification disagree, the specification wins — or the specification is
  fixed.** What is never done is leaving the disagreement unspoken.

**States:** `not started` · `partial` · `done` · `under review`. Any row past *not started*
carries the path to the code that implements it.

**Phase** points at `PLAN.md`, which orders the work by dependency. This file answers *how much
is built*; that one answers *what comes next and why*.

> `SPECS.md`, `PLAN.md` and `AGENTS.md` live in the
> [almena-network](https://github.com/almena-network/almena-network) repository.

The link needs no second act: the element names its parent, and the act only enters the record because the parent's owners signed it at the class it costs — so nobody hangs one off an organisation they do not govern, and there is no window in which a claim stands unanswered. | §7.2 · §7.3 · §4.9 (certification) | One party's signed statement about another, as an object with a chain of its own and a subject; three grades from a **closed** vocabulary; anybody may certify anybody; never retroactive | F6 | yes — `crates/almena-store/src/certification.rs`. It does not live on the chain of the entity it is about, for the reason a vote does not live on the proposal's: **nobody writes in somebody else's chain**, and being certified must not mean letting another party append to your own history. The grade's vocabulary is closed, so a number this build does not know is refused rather than read as the nearest one it does — *a grade slightly above the one I know* is exactly the reading that would be dangerous. Nothing is refused on the grounds of **who** is certifying (`SPECS.md §7.3`): what a statement is worth is decided by who made it and by the reader, who chooses their own root. It is found by the party affected, because a certification carries its subject the way a contradiction does — an entity that could not ask *what has been said about me* would find out because a customer mentioned it. **Almena Government signs with the one key the act that opened the network gave it**; its composition under `SPECS.md §7.1` is F10's, and inventing owners for it now would be putting state in the record nobody decided |
| §7.8 · §7.10 (record half) | Withdrawal signed and never retroactive; **immediate on risk, notice and 720 epochs on non-compliance**; a published reason always, in both languages; the right of reply | F6 | yes — the two speeds are separate causes with separate effects, because one is an emergency and the other a formality, and treating the second as the first is how a procedure becomes the end of somebody's business. **A reason with no language the reader has is refused at admission**, so a decision with no published ground is never in the record: `SPECS.md §9.4` made the seal a permission, and a gate without a reason is arbitrariness. A withdrawal is said once and its date is not moved afterwards, or a notice period would be one somebody could shorten after announcing it. The reply is `crates/almena-store/src/reply.rs`: **its own object, published once and never edited**, by the party the decision was about and by nobody else — a reply the decider could withhold would be a right the decider grants, and one anybody could publish would let a stranger answer in somebody else's name |
| §7.5 (alias) · §7.6 | An alias derived from a verified domain, only for certified entities, unique, quarantined for 2 160 epochs; an address only for organisations and consistent with the domain | F6 | mostly — `crates/almena-store/src/entity.rs`. **The domain decides which name and the seal decides whether there may be one**: without that second half whoever registered a look-alike would hold the look-alike name with perfect technical legitimacy. The character set is restricted and a name is refused rather than repaired, because internationalised domains admit homoglyphs that render identically. A name is one entity's across the whole record, and one given up cools for ninety days so nobody inherits the reputation of whoever left. An address exists only on an organisation — **there is nowhere to put one on a person**, which is the enforcement rather than a rule to remember — and is held to a domain that was proved. What is **not** here is *accepted*: how many signed roots a concession waits for is the reader's policy and not the protocol's (`SPECS.md §4.4`), and it is `crates/almena-store/src/firm.rs`'s `Wanted`, with a conservative default |
| §7.4 · §7.5 (uniqueness) | Domains: bidirectional TXT proof, revalidation every 720 epochs, **one domain to one entity** | F5 | mostly — the record carries the claim and **the epoch it was last proved in**, and `stands()` says when it owes another proof. Checking DNS is deliberately not a condition of admission: validity has to be decidable from the act and the record alone, or two honest nodes disagree because one was asked while a resolver was down. The reader is `crates/almena-lookup`'s `domain`, which tells *nobody claims this* from *nobody could be asked*. Uniqueness **is** enforced across the record: a second claim on a bound domain is refused until the first releases it, which puts the tie-break back with whoever controls the domain. What remains is the alias (F6) |
| §12.1 | Closing an entity: a state with a date and never a deletion, and the closer chooses what happens to what is outstanding | F5 | mostly — closed with its epoch, and the choice about outstanding credentials carried as the closer made it. What acts on that choice is revocation, which is F8 |
| §10.2 | Status-list distribution: only the version hash in the log, deterministic replication, publication node, *replica first* | F8 | not started |
| §11.12 | Deferred effect for operations signed by the control key alone, and validation of `cancel` from a live device or a guardian quorum | F3 · F9 | mostly — `crates/almena-store` (`chain.rs`, `checkpoint.rs`, `parameter.rs`). What the control key signs alone enters the record at once and lands `CONTROL_WAITS` (72, versioned) epochs later; `State::Holder` carries `frozen` and a `waiting` queue, and the effect is materialised by `come_due(moment)` so two nodes hearing one chain in different orders compute one account. Any current device cancels a waiting act by name, never the one its own removal names; the words never cancel. Freeze is the one immediate control act and a frozen account admits nothing but a device's cancellation; unfreeze concedes, so it waits like anything else the words sign alone. The checkpoint verifier replays the same rules. **Adversarially reviewed** (five lenses); five confirmed defects closed with attack-first regression tests: a back-dated `issued` (closed by the invariant that an act may not precede the act it follows, `Refused::BeforeItsPredecessor`), a frozen account refusing a fork instead of keeping it (freeze taken out of `entitled`), the replay honouring a device's self-removal cancel (`struck_out` mirrors admission), an unbounded pending queue costing O(L²) (`CONTROL_PENDING_MOST`, `Refused::TooManyWaiting`), and a known-but-unbuilt kind going opaque in admission but skipped by the verifier (`unreadable` = cannot-apply). Guardian-quorum `cancel`/`recover` and `set_guardians` stay F9, so the node resolves neither; a checkpoint does not yet attest `frozen` or the pending queue, a precondition for wiring checkpoint bootstrap — and **half of it is now closed by refusing rather than by carrying**: nothing summarises an account with an asking in flight, from the control key or from a device. A summary has nowhere to say what is waiting, and a node serves the last summary and what followed, so one written over an asking is an asking no reader ever sees — landing seventy-two epochs later on a state nobody was shown, which is §11.12's notice deleted by arithmetic. Both acts are ones the control key alone may write, so it was a thing to be done on purpose. It is the rule a frozen account already lived under, for the same reason: a summary is routine, and an account with something in flight is the opposite of routine. What waits comes due within one window, so what this refuses is never permanent. **And the holder's app is held to these rules from the outside**: `crates/almena-store/tests/what_the_client_composes.rs` takes bytes that program actually produced — a creation, a device the words ask for, a device another device adds, a removal, a cancellation, and the two acts of the panic path (§11.8) — and puts each through the admission every act goes through, so a disagreement between the two implementations fails here as a refused act and there as a changed constant, rather than in front of somebody whose laptop will not join their account. **And a critical field this build cannot read now stops it here too** (§4.8 rule 4): an act carrying an odd field with no meaning here is kept and propagated — rule 1, replication does not require understanding — and the object goes opaque rather than being resolved as though the act had not been written, which is rule 2. Asked after the signature, so only a key the account authorises can do it; and the vocabulary is one list for every holder kind, pinned against the holder app's own copy in the twin, because a drift there is not a disagreement but an account one side resolves and the other declares opaque for ever |

## Replicated code — rows that exist twice

**The repositories share no code** (§13.13). The format lives here **and** in `client`, written
twice on purpose so that neither project owns the other's ground. What keeps the two copies from
drifting is not a library: it is **the golden vectors as the contract** — the same case file in
both repositories, each running it against its own implementation.

| Replicated with | Which rows | What a change owes |
|---|---|---|
| `client` | §3.1 (identifier), §4.9 (canonical CBOR, operation schema), §4.11 (suite), §4.14 (epoch arithmetic) | The same change in the other repository, **and the vector that covers the new case in both** — a case covered here and not there is where divergence enters |

## What is **not** this repository's

Named because the boundary is where duplicated work happens:

- **`did:peer` and the relationships that use it** (§3.3) — the holder's app. What this repository
  holds is the letterbox: it routes by the address a relationship gave out and never learns what
  that address is for.
- **Composing and drawing anything a person consents to** (§9.2) — the client draws it; the node
  never serves a screen.
- **The trust decisions themselves** (§7) — the node validates operations and counts signatures;
  who deserves a seal is Almena Government's judgement through the Registry.
- **The public catalogue and monitoring portal** (§13.6, §5) — the Registry serves them; this
  repository serves the API they read.
- **Holding or presenting a credential** (§9.5, §11) — the client. The node never sees one, and
  the SDK published here builds and verifies them without ever holding one either.
