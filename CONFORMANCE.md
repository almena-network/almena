# Conformance — `almena`

Which sections of `SPECS.md` this repository owns, and how much of each is built. The rule is
**`SPECS.md §13.13`**:

- **The matrix belongs to the project.** The specification says what must exist; this file says
  where it lives and how far along it is. `SPECS.md` keeps nobody's accounts.
- **A section closes where it is implemented, not where it is read.** A row moves to *done* when
  it points at code whose behaviour matches its section — not when something compiles or its
  tests pass.
- **When `SPECS.md` changes, the affected rows go to *under review*** until someone checks them
  against the new text.
- **If code and the specification disagree, the specification wins — or the specification is
  fixed.** What is never done is leaving the disagreement unspoken.

**States:** `not started` · `partial` · `done` · `under review`. Any row past *not started*
carries the path to the code that implements it.

**Phase** points at `PLAN.md`, which orders the work by dependency. This file answers *how much
is built*; that one answers *what comes next and why*.

> `SPECS.md`, `PLAN.md` and `AGENTS.md` live in the
> [almena-network](https://github.com/almena-network/almena-network) repository.

That was the attack the refusal existed for — both acts are ones the words alone may write, so a thief could summarise their own asking out of every reader's sight — and a writer's refusal only ever bound the writers who kept it. **And the holder's app is held to these rules from the outside**: `crates/almena-store/tests/what_the_client_composes.rs` takes bytes that program actually produced — a creation, a device the words ask for, a device another device adds, a removal, a cancellation, and the two acts of the panic path (§11.8) — and puts each through the admission every act goes through, so a disagreement between the two implementations fails here as a refused act and there as a changed constant, rather than in front of somebody whose laptop will not join their account. **And a critical field this build cannot read now stops it here too** (§4.8 rule 4): an act carrying an odd field with no meaning here is kept and propagated — rule 1, replication does not require understanding — and the object goes opaque rather than being resolved as though the act had not been written, which is rule 2. Asked after the signature, so only a key the account authorises can do it; and the vocabulary is one list for every holder kind, pinned against the holder app's own copy in the twin, because a drift there is not a disagreement but an account one side resolves and the other declares opaque for ever |

## The issuer and verifier SDK

Published from here and not a project of its own (§13): the same house that validates these rules
on one side of the wire writes the library that speaks them on the other, so a disagreement
between SDK and node is a bug inside one repository rather than an argument between two.

**It is three crates, each with one job.** `almena-credential` is the format and nothing else — it
resolves nothing, fetches nothing and reaches nowhere; `almena-status` is the bitstring, the window
it covers and the rule that decides whether one is fresh enough to use; `almena-sdk` is the two
façades over both. What none of them does is decide whether anybody is to be trusted: *how many
nodes to ask* and *whose seal is worth anything* are the reader's own policy (§4.4, §7.3), and a
library with a default for either would be one making somebody's trust decisions under that name.

**And a fourth thing beside them, since 2026-09-02**: `partner/`, the binary `almena-partner` — a
reference issuer and verifier on the SDK that relates to a holder through their mediator, issues,
revokes and serves the presentation request of §9.2 against a real node, so that the rules the node
applies are seen to work from the other side of the wire. It is a row below since 2026-09-02, and
it invents no data (§7.9) — what it issues is what its operator typed.

## Replicated code — rows that exist twice

**The repositories share no code** (§13.13). The format lives here **and** in `client`, written
twice on purpose so that neither project owns the other's ground. What keeps the two copies from
drifting is not a library: it is **the golden vectors as the contract** — the same case file in

## What is **not** this repository's

Named because the boundary is where duplicated work happens:

- **`did:peer` and the relationships that use it** (§3.3) — the holder's app. What this repository
  holds is the letterbox: it routes by the address a relationship gave out and never learns what
  that address is for.
- **Composing and drawing anything a person consents to** (§9.2) — the client draws it; the node
  never serves a screen.
- **The trust decisions themselves** (§7) — the node validates operations and counts signatures;
  who deserves a seal is Almena Government's judgement through the Registry.
- **The public catalogue and monitoring portal** (§13.6, §5) — the Registry serves them; this
  repository serves the API they read.
- **Holding or presenting a credential** (§9.5, §11) — the client. The node never sees one, and
  the SDK published here builds and verifies them without ever holding one either.
